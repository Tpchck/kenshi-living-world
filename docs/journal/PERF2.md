# PERF фаза 2 — журнал (2026-11-13)

Повод: в реальной игре KMM_Gov троттлил модули (conductor 1.00 мс, self 1.12 мс, stock 1.00 мс при бюджете 0.6 мс). Фаза 1 дала общий снимок `KMM_Gov.snapshot`; фаза 2 переводит на него остальные модули с обходами и режет дорогие места Self и Conductor.

## Что изменено
Резервные копии (до правок): `build\KMM_Stock\_dev\kmm_stock_pre_perf2.lua.txt`, `build\KMM_Town\_dev\kmm_town_pre_perf2.lua.txt`, `build\KMM_Elite\_dev\kmm_elite_pre_perf2.lua.txt`, `build\KMM_Conductor\_dev\KMM_Self_pre_perf2.lua.txt`, `build\KMM_Conductor\_dev\KMM_Conductor_pre_perf2.lua.txt`.

Паттерн везде как в Traces/Self: `KMM_Gov.snapshot(ttl)` под pcall; нет Gov, Gov.snapshot бросил исключение или вернул nil -> прежний собственный обход (код не удалён). Перед действием над персонажем из снимка (мог устареть до ttl) — живая проверка `isDead`.

- **KMM_Stock** (`scripts\init\kmm_stock.lua`): `nearby_npcs` берёт снимок (ttl `cfg.snap_ttl` = 4 с, выключатель `cfg.use_snapshot`), отдаёт ещё и карту ch -> запись. `traders`, `npc_buy`, `sales` берут признак торговца (`rec.trader`), город (`rec.town`) и фракцию (`rec.fid`) из записи вместо повторных `getPlatoon/getIsTrader/getCurrentTownLocation/getFaction`. Фильтр dead/unique/радиус — по полям записи (unique теперь читается только у тех, кто в радиусе). Плюс `as_building`/`key_of` без замыканий на каждый вызов (микро).
- **KMM_Town** (`scripts\init\kmm_town.lua`): `scan` — дешёвый фильтр по снимку (dead, позиция, `rec.town` как готовый `getCurrentTownLocation`), `isAnimal`/`isDead` вживую только у тех, кто в городе рядом; разбор персонажа вынесен в `classify` (общий для снимка и прежнего обхода). Конфиг `use_snapshot`, `snap_ttl` = 4. `town_sid_of(obj, t0)` принимает уже известную локацию.
- **KMM_Elite** (`scripts\init\kmm_elite.lua`): `elite_alive` читает `rec.tsid` (шаблон отряда) из снимка; `isDead` у совпавшего — вживую. Параметры `P.use_snapshot`, `P.snap_ttl` = 4 (в данных не заданы, умолчания в коде).
- **KMM_Self** (`scripts\init\KMM_Self.lua`): `scan` в два прохода. Проход 1 — только группировка по платунам и `r.combat` (останавливается после первого боевого бойца отряда). Проход 2 — только для боевых отрядов: `down`, `unique`, вожак (`getSquadLeader` один раз и только если в отряде кто-то лежит). Решения в `scan`/`faction_avoid` принимались только у `g.combat`, остальное считалось впустую у мирных отрядов. Расстояние сравнивается в квадратах (без sqrt).
- **KMM_Conductor** (`scripts\init\KMM_Conductor.lua`): `scan_loaded` (раз в 2 с по всем NPC: `getGameData` + `getFaction` + `getData` на каждого) переведён на снимок (`P.scan_snapshot` = false выключает, `P.scan_snap_ttl` = 4 как у Traces — меньший ttl у одного модуля учащает общую перестройку снимка). `getGameData` читается только если есть ожидающая материализация (`S.pending`), `try_gear` вызывается только если у какой-нибудь фракции есть сдвиг богатства (`gear_possible`); иначе тик ничего не делает, и `appeared` чистится как раньше. `write_relations`: ранний выход при пустой очереди `S.dirty_rel` (был подсчёт и обход каждый тик). Остальной `on_tick` (`advance`, `try_dispatch`, `WSL.tick`) уже дешёвый: всё по игровым дням/пустой очереди.

Живой API не нарушен: у Faction только `f:getData() or f.data`; здание — `o:getHandle():getBuilding()`; createRandomSquad (15 аргументов, hand, squadType числом) не трогался; `Character:getPlatoon()` -> ActivePlatoon (`ap.me`, `ap:getIsTrader()`); при загрузке скриптов ничего тяжёлого не добавлено (снимок берётся только внутри тика).

## Замер (`build\KMM_Conductor\_dev\test_perf2.py`, N = 200 NPC в заглушке)
Колонки: вызовы API персонажей на окно (каждый метод NPC обёрнут счётчиком) собственные у модуля / «+общий снимок» (построение снимка, его делят Traces, Self, Conductor, Rumors и т. д.; в тесте его строит условный потребитель с ttl 4 с, как Traces); обходы `getCharacterUpdateList` (только собственные); мс Lua модуля (QueryPerformanceCounter).

| Модуль / окно | API до | API после (Gov) | API после (без Gov) | обходов до -> после | Lua мс до -> после (Gov) |
|---|---|---|---|---|---|
| Stock, 600 с | 178658 | 23193 (+120000 общий) | 178658 | 205 -> 0 | 10.8 -> 15.9 (+72 общий) |
| Town, 600 с (~8 циклов) | 28380 | 10140 (+72120 общий) | 28380 | 20 -> 0 | 5.3 -> 5.3 (+104 общий) |
| Elite, 120 тиков, элита жива | 24240 | 120 (+120600 общий) | 24240 | 120 -> 0 | 10.3 -> 5.1 (+36 общий) |
| Elite, элита мертва (1 спавн) | 202 | 1 (+120600 общий) | 202 | 1 -> 0 | 0.6 -> 0.8 |
| Self, 10 с | 3104 | 1603 (+1150 общий) | 2020 | 2 -> 1 | 0.79 -> 0.53 |
| Conductor scan_loaded, простой мир, 10 с | 2000 | 0 (+2000 общий) | 2000 | 5 -> 0 | 0.74 -> 0.05 |
| Conductor, экипировка + материализация, 10 с | 2505 | 505 (+2000 общий) | 2505 | 5 -> 0 | 0.81 -> 0.33 |

Как читать. Общий снимок в игре строится и без Stock/Town/Elite (его уже просят Traces и Self каждые 3.5–4 с), поэтому выигрыш модуля — это колонка «API после». Если бы Gov был единственным потребителем (только один модуль), общий снимок дороже старого обхода: он читает 5 полей у каждого из 200 NPC, а Elite/Town раньше читали меньше. Так что выигрыш реален только при разделении снимка — именно как в игре, где его уже строит Traces.
Время Lua в заглушке — это почти только накладные расходы интерпретатора (вызов API в заглушке стоит ~50 нс, в движке на порядки дороже), поэтому метрика, которой верить, — число вызовов API. Stock в заглушке даже чуть медленнее по мс (лениво вычисляемые поля через метатаблицу и pcall быстрее не исполняются JIT), но в 7.7 раза меньше вызовов API.

## Риски и тонкости
- Устаревание снимка до 4 с: позиции/«мёртв» в Stock/Town/Elite могут отстать. Смягчено живой проверкой `isDead` перед действием (Stock: торговец/житель, Town: персонажи города, Elite: совпавший боец); в Elite дополнительно страхует `alive_grace` 40 с после спавна. Радиусы сканов (300–2500) на порядок больше сдвига NPC за 4 с.
- Town: лимит `max_scan_chars` (80) теперь считает записи снимка (без игроков), а не весь список; при отряде >80 персонажей набор просматриваемых может немного отличаться от прежнего (в игре и раньше зависел от порядка хеша).
- Conductor `scan_loaded`: окно материализации «момент загрузки зоны» (window_seconds 15 с) смотрит снимок до 4 с давности — появление персонажа замечается на ≤ 4 с позже, в окно 15 с укладывается. Для выключения: `params.scan_snapshot = false` в conductor.json.
- Ттл разных потребителей разный (Self 3.5, Gov по умолчанию 2): меньший ttl чаще перестраивает общий снимок. Для Stock/Town/Elite/Conductor выбрано 4 с (как Traces).
- Не сделано: отдельный round-robin сканов в Conductor — после перевода на снимок тик scan_loaded в простое стоит ~0; `world_step` (симуляция по игровым дням) не трогался, он уже ограничен `tick_days`. `sales` в Stock по-прежнему читает инвентари лавок/торговцев целиком (counts_of) — это логика определения продажи игрока, менять без игры нельзя.
